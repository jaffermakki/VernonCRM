# Deploying TechPro+ CRM

Two supported paths: **Render** (recommended — flat pricing, backups
included from the cheapest paid tier) or **Railway** (usage-based
pricing, backups gated to the Pro plan). Both need the same two secrets
generated once, up front.

---

## Before either platform: generate your two secrets

Run these locally (needs Python + the `cryptography` package — already
in `requirements.txt`, or just run `pip install cryptography` first):

```bash
# SETTINGS_ENCRYPTION_KEY — encrypts SMTP/Twilio credentials at rest in the DB
python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

# SESSION_SECRET — signs staff login session cookies
python3 -c "import secrets; print(secrets.token_hex(32))"
```

Save both output strings somewhere safe (a password manager). You'll
paste them into the platform's dashboard in a moment. **Never commit
these to git or put them in `render.yaml`/`railway.json`** — that's
why both config files leave them as manually-set secrets rather than
hardcoding them.

---

## Option A: Render (recommended)

1. Push this repo to a GitHub repo (private is fine).
2. In the Render dashboard: **New +** → **Blueprint** → connect the repo.
   Render reads `render.yaml` automatically and shows you a preview of
   what it's about to create: one web service + one Postgres database.
3. Click **Apply**. Render provisions both and wires `DATABASE_URL`
   from the database to the web service automatically — you don't type
   a connection string anywhere.
4. Once the service exists, go to its **Environment** tab and add the
   `SETTINGS_ENCRYPTION_KEY` you generated above (`SESSION_SECRET` is
   already auto-generated by the blueprint — leave it alone).
5. Redeploy (Render prompts you to after adding the env var).
6. Visit the service's `.onrender.com` URL. Log in with PIN `1234`
   (the seeded Owner account) and **change it immediately** from the
   Staff page.

**Cost:** ~$13/mo flat (Starter web $7 + Basic-256mb Postgres $6).
Point-in-time recovery is included at this tier.

**Custom domain:** Render → your service → Settings → Custom Domains.
Free, just point a CNAME at the `.onrender.com` address.

## Option B: Railway

Railway doesn't support one-file blueprint provisioning the way Render
does, so the database and secrets are added through the dashboard:

1. Push this repo to GitHub.
2. Railway dashboard → **New Project** → **Deploy from GitHub repo** →
   select this repo. Railway auto-detects the `Procfile` and
   `runtime.txt` and builds it (`railway.json` in this repo pins the
   health check and restart policy on top of that).
3. In the same project: **+ New** → **Database** → **Add PostgreSQL**.
4. Click into your web service → **Variables** tab → **+ New Variable**
   → **Add Reference** → select the Postgres service's `DATABASE_URL`.
   This wires them together without you copy-pasting a connection
   string.
5. Still in Variables, manually add:
   - `SESSION_SECRET` = (the value you generated above)
   - `SETTINGS_ENCRYPTION_KEY` = (the value you generated above)
6. Deploy. Railway gives you a `.up.railway.app` URL — visit it, log in
   with PIN `1234`, change it from the Staff page.

**Cost:** $5/mo Hobby plan minimum, but realistically **$10–20/mo**
once actual usage is billed on top of the included credit — this is
metered, not flat, so it moves month to month. **Automated backups are
Pro-plan-only ($20/mo min)** — on Hobby, either add Railway's
one-click "Postgres Daily Backups" template yourself, or accept the
risk. This is the main reason Render is the default recommendation
above.

## Either platform: the health check

Both configs point at `GET /healthz`, which returns `{"status": "ok"}`
without touching the database or requiring login — deliberately so a
briefly-reconnecting DB doesn't cause a false-negative restart loop.

## Either platform: what NOT to do

- Don't set `SETTINGS_ENCRYPTION_KEY` to Render's auto-generated
  value or any random string typed by hand — it must be a real Fernet
  key from the command above, or the app silently falls back to
  storing SMTP/Twilio credentials **unencrypted** rather than erroring
  loudly. This is why `render.yaml` deliberately does *not* use
  `generateValue: true` for that one variable.
- Don't lose the `SESSION_SECRET`/`SETTINGS_ENCRYPTION_KEY` values once
  set — rotating `SETTINGS_ENCRYPTION_KEY` makes any already-encrypted
  settings (SMTP password, Twilio token) undecryptable; you'd need to
  re-enter them in Settings after a rotation.
